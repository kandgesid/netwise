# Netwise Content & Flow Strategy

Author: Content & Flow Strategist agent (analysis-only; no `src/` files were modified).
Scope: every file under "What to review" in the assignment — `src/components/chapters/*`, `src/data/*`, `src/components/sandbox/Sandbox.tsx`, `src/components/reference/CertificateTabs.tsx`, `src/components/reference/Glossary.tsx` — read in full, plus `src/App.tsx` and `src/lib/autoLink.tsx` for architectural context.

This document is organized in reading order (Hero → Ch1 → Ch2 → Ch3 → Ch4 → Ch5 → Ch6 → Sandbox → Reference → Glossary). Each finding names the exact file and passage, explains what's wrong or weak, and gives a concrete fix an implementer can execute without further context. A prioritized punch list is at the end.

A structural note up front, since it recurs across several findings below: well-regarded interactive-explanation design (the "explorable explanations" tradition — Bret Victor's original essay, Nicky Case's `Parable of the Polygons` and follow-on writing) converges on a "guided discovery" pattern: introduce one mechanic in isolation, let the reader play with it until it's intuitive, *then* combine it with the next mechanic, and only assemble the full system once every piece has been individually earned. Several of the findings below (Chapter 4's density, Chapter 5's unexplained "first match wins," the Chapter 3 card-before-stepper ordering) are instances of that discipline being skipped — a concept or a combination of concepts appears before the reader has had a chance to build the isolated intuition it depends on.

**Finding C3-2 — high priority (technical accuracy). Inbound Inspection's step "Firewall computes the same session key" overstates what holding the server's private key actually gets you, and it directly contradicts what Chapter 4 teaches about ephemeral key exchange.**
✅ **Implemented.** Added the static-RSA-vs-ephemeral-ECDHE/DHE caveat to `handshakeSteps.ts`'s `inbound.note` and `inbound.steps[3]` (retitled "Firewall computes the same session key (with static RSA)"), plus a matching adjustment to `inbound.steps[4]`. Same caveat mirrored into `certificates.ts`'s `inbound` tab as a new "The catch:" point (see R1 below).
`handshakeSteps.ts`, `inbound.steps[3]` (lines 51): *"Because the firewall was given the server's private key ahead of time, it can independently derive the same session key being negotiated, without inserting itself as a third party into the handshake."* This is only true when the negotiated key exchange is **static RSA** (client encrypts the pre-master secret directly with the server's RSA public key, so anyone holding the matching private key can decrypt it). It is **not** true when the connection uses ephemeral (EC)DHE key exchange — and Chapter 4 tells the reader, in the very next chapter, that *"Modern TLS almost always uses an ephemeral version... A brand-new key pair is generated just for this one session, then thrown away afterward"* (`Chapter4KeyExchange.tsx` lines 22–26) and that this is precisely what gives TLS forward secrecy. With ECDHE, the server's static private key is used only to *sign* the ephemeral parameters for authentication (which Chapter 4's own `CipherDecoder` RSA entry correctly states: *"RSA is the authentication algorithm... separate from whatever is doing the actual key exchange,"* `cipherSuite.ts` line 9) — it cannot be used to derive the session key, because the session key is derived from the ephemeral Diffie-Hellman exchange, not from the RSA key pair at all. So Chapter 3's inbound-inspection scenario and Chapter 4's key-exchange explanation are, taken together, internally inconsistent: Ch3 implies "hold the private key → you can decrypt," Ch4 explains why that stops being true the moment forward secrecy is in play — which Ch4 says is the normal case for modern TLS. This isn't a pedantic nitpick: it's a well-known real-world gotcha (firewall/proxy products that do inbound SSL decryption via imported private key generally cannot decrypt sessions negotiated with forward-secret cipher suites unless those cipher suites are specifically restricted on the server, or the firewall uses a different technique) and it's exactly the kind of "sounds right, isn't" detail that undermines trust in a learning tool once a reader with real experience notices it.
The same simplification is repeated in `src/data/certificates.ts`, `inbound` tab (lines 25–33): *"What the firewall holds: the actual server certificate and its matching private key... it decrypts in place."* No caveat about cipher suite / key exchange mode appears there either.
*Fix:* Add a caveat sentence to `handshakeSteps.ts` `inbound.steps[3].body` (and optionally `inbound.note`, line 46) clarifying that this private-key-based decryption model works cleanly with non-ephemeral (static RSA) key exchange, and that with the ephemeral (ECDHE/DHE) exchange Chapter 4 describes as the modern default, a firewall doing inbound inspection this way generally needs those forward-secret cipher suites restricted on the server (or a different interception technique) — otherwise it can't derive the session key from the private key alone. Something in the spirit of: *"This works cleanly as long as the negotiated cipher suite uses plain RSA key exchange. If the server negotiates an ephemeral (ECDHE/DHE) exchange instead — the forward-secrecy mode covered in Chapter 4 — the static private key alone isn't enough to derive the session key, which is why real inbound-decryption deployments often have to restrict which cipher suites the server offers."* Mirror the same caveat into `certificates.ts`'s `inbound` tab point list (add a `CertPoint` after "What the firewall holds"). This is the single most important technical-accuracy fix in this review — it's the one place the site teaches two things that can't both be true as currently written.

**Finding C3-4 — medium priority (technical accuracy / oversimplification). The handshake steps blend TLS 1.2 and TLS 1.3 mechanics without saying so, and the blended version happens to be the one that's more favorable to the "passive firewall can just watch" story than TLS 1.3 actually allows.**
✅ **Implemented.** `passthrough.steps[1].body` in `handshakeSteps.ts` now distinguishes TLS 1.2 (certificate visible on the wire) from TLS 1.3 (certificate encrypted, destination still visible via SNI), using close to the doc's suggested wording.
`passthrough.steps[1]` (`handshakeSteps.ts` line 22): *"Client and server negotiate TLS and exchange the real server certificate directly. The firewall sees this happen but isn't a party to it."* This describes the certificate being visible to an on-path passive observer, which is accurate for TLS 1.2 but not for TLS 1.3: in TLS 1.3 the server's Certificate message is encrypted (protected by handshake traffic keys derived right after the ServerHello / key_share exchange), so a purely passive firewall cannot actually see the certificate in the clear — it can typically still identify the destination via the cleartext SNI field in ClientHello, but not by reading the certificate itself. In TLS 1.2 the real server certificate is visible on the wire at this point; in TLS 1.3 (the common case today) it's encrypted, though the destination is still visible from the ClientHello's SNI field. Either way, the firewall watches this happen without being a party to it."* Keep it to one added sentence — the goal is not to introduce a TLS-version tangent, just to not assert something as universally true that stopped being true for most real-world traffic.

**Finding C4-2 — medium priority (technical accuracy / oversimplification). The four-part cipher suite name shown in `CipherDecoder` (ECDHE / RSA / AES_256_GCM / SHA384) is TLS 1.2-style naming, but the surrounding copy frames everything as "modern TLS" without ever distinguishing the two.**

`cipherSuite.ts`'s `CIPHER_PARTS` decodes a classic OpenSSL/TLS-1.2-style cipher suite string (e.g. `ECDHE-RSA-AES256-GCM-SHA384`) into four independently-negotiated pieces. That's a real, still-common format (a lot of firewall/proxy documentation displays cipher suites this way, especially in decryption/inspection contexts where TLS 1.2 is still frequently in play), so it's not *wrong* to teach — but TLS 1.3 restructured cipher suite naming specifically to drop the key-exchange and authentication algorithms from the suite name (TLS 1.3 suites look like `TLS_AES_256_GCM_SHA384` — just AEAD cipher + hash; key exchange group and signature algorithm are negotiated separately via extensions, and only ephemeral exchange is supported at all). Chapter 4's own text says "Modern TLS almost always uses an ephemeral version" (implying TLS 1.3 territory) right before handing the reader a TLS-1.2-flavored four-part name to decode, without ever flagging that these are two different eras' conventions.

This keeps the existing example (which is a fine, concrete teaching device) while not letting the reader walk away thinking every TLS connection today literally negotiates a suite that looks like this string.

✅ **Implemented.** Appended a clarifying clause to the SHA384 entry in `cipherSuite.ts` distinguishing its handshake/key-derivation integrity role from GCM's per-message authentication.

**Finding C5-3 — low priority (technical accuracy nuance). "Bypass" is presented as a third co-equal policy action alongside "Decrypt" and "No decrypt," which slightly overstates how this is usually implemented in real products.**
✅ **Implemented.** Appended a trailing clause to `ACTIONS[2].text` (Bypass) in `Chapter5DecryptionPolicies.tsx` noting most real products handle this via an exclusion list or decryption-profile setting rather than a literal third rule-action value. Kept the three-card model as-is, since the doc treats pedagogical simplicity here as defensible.
`ACTIONS[2]` (`Chapter5DecryptionPolicies.tsx` lines 7): *"Bypass: Decryption processing is skipped entirely for this traffic, usually for performance, or because an app is known to break under interception, like ones that pin certificates."* In practice (e.g. Palo Alto-style decryption policy, which the site's App-ID/User-ID/Content-ID vocabulary is clearly modeled on — see Finding G1 below), a decryption policy rule's action is typically just "Decrypt" or "No Decrypt"; certificate-pinned or otherwise interception-hostile apps are usually handled via a separate exclusion list or decryption-profile setting, not a third selectable value in the same action field as the other two. Presenting all three as parallel, equally-weighted options in one three-card row is a defensible simplification for teaching purposes (it keeps the mental model to "three possible outcomes," which is genuinely useful), but it doesn't map cleanly onto how the action actually appears in a real product's UI.
*Fix:* This is a judgment call for the project owner on how much real-world fidelity matters here. If pedagogical simplicity should win, leave it as-is (it's not *false*, the three outcomes are all real things that happen), but consider softening `ACTIONS[2]`'s label or adding a trailing clause noting that in most real products this is handled via an exclusion list rather than a rule action, so a reader who later opens a real firewall's decryption policy UI doesn't go looking for a literal "Bypass" dropdown option that isn't there in that specific form.

**Finding C6-1 — medium priority (structure). `DEPLOY_STEPS` mixes true sequential setup steps with parenthetical caveats inside one numbered list, which implies a false order.**

## Sandbox (`src/components/sandbox/Sandbox.tsx`, `src/data/sandboxScenarios.ts`)

**Works well.** This is the strongest single piece of writing/design on the site. The `SectionHead` intro (lines 122–127) states the core lesson in one clear paragraph before any interaction starts ("a rule written for a port number can be fooled, a rule written for an actual application identity can't, and a rule written for a specific person can enforce things neither of the others can"), then the interactive lets the reader prove that claim to themselves rather than just being told it. The terminal-log motif (per CLAUDE.md's design intent, this is the one place decorative-feeling motion is justified because it *is* the feedback) works well here — each `LogEntry`'s `detail` text (`sendPacket()`, lines 72–110) explains *why* the match did or didn't happen, not just the allow/block verdict, which reinforces the underlying mental model on every single click rather than just the first one. The "Try it: load a rule nothing matches" button (`tryImplicitDenyExample`, lines 112–118) is a nice piece of design — it pre-loads a guaranteed-to-surprise scenario (an Allow rule for port 80 against traffic that's actually on 443) rather than leaving implicit-deny as something the reader has to stumble into by accident.

**Finding S1 — low priority (consistency). Sandbox's mental model is "one packet, one instant verdict," which is a reasonable simplification but is worth being deliberate about, not accidental.**
✅ **Implemented.** Added the suggested italic footnote near the Sandbox console output in `Sandbox.tsx` acknowledging real firewalls typically need several packets of a session before App-ID can confirm the application.
The UI calls the action "Send packet →" (line 236) and the log entry says `send-packet` (line 251), continuing the "packet" framing Chapter 1 established (`FirewallCheckpointViz`'s individual animated packets). Real App-ID/Content-ID-style application identification generally operates on a flow/session — a firewall typically needs to see several packets of a connection before it can confidently identify the application, not just the first one — so "one packet in, one instant allow/block verdict out" is a simplification of how this actually behaves operationally. This is a defensible, even good, simplification for a beginner-facing sandbox (it keeps the unit of interaction intuitive and matches the visual language Chapter 1 already established), so this is not a "fix this" finding, just a "confirm this is a deliberate choice" one.
*Fix (optional, low priority):* If it's worth a nod to accuracy without disrupting the UX, a one-line footnote near the Sandbox's console output (e.g. "Real firewalls usually need a few packets of a session before App-ID can confirm what's actually running — this sandbox shows the eventual verdict instantly for clarity") would cover it. Not required; flagging so it's a conscious decision rather than an unexamined one.

**Finding S2 — see Finding C1-1 / C5-2.** ✅ **Implemented** — see C5-2; the new `PolicyEvaluator` in Chapter 5 is the hands-on "first match wins" demo this finding asked for (the Sandbox itself was left as a single-rule interactive, per the doc's own framing of this as a Chapter 5 addition rather than a Sandbox rebuild). The Sandbox is where "first match wins across an ordered rule list" would most naturally get a hands-on demonstration, since it's already the site's rule-matching interactive — but as built, it only ever evaluates one rule against one traffic scenario, so that specific concept (asserted in Chapter 5, defined in the Glossary) never gets the same "prove it to yourself" treatment as port/App-ID/User-ID matching does. ## Reference — Glossary (`src/components/reference/Glossary.tsx`, `src/data/glossary.ts`)

**Works well.** The intro line ("No definitions written to impress, just what each term means and why it exists") is a good closing-voice match for the site's overall register, and most entries follow through on that promise — plain, short, no padding.

**Finding G1 — high priority (technical accuracy / trustworthiness). App-ID, User-ID, and Content-ID (and, less centrally, "Forward Trust"/"Forward Untrust" CA terminology) are presented throughout the entire site as if they were generic, vendor-neutral firewall industry terms. They are not — they're Palo Alto Networks' specific product terminology for these capabilities.**
✅ **Implemented.** Added the vendor-attribution paragraph to Chapter 3's new "Three lenses the firewall applies" `Card` in `Chapter3Handshake.tsx` (first point of contact with this vocabulary in reading order, per the doc's placement guidance), close to the doc's suggested wording. Reinforced with a shorter cross-reference appended to the Glossary's `App-ID` entry in `glossary.ts`. Did not touch "Forward Trust"/"Forward Untrust" naming itself (used descriptively as internal CA labels, not presented as universal vendor-neutral terminology the way App-ID/User-ID/Content-ID were) or reword the vendor-specific terms elsewhere (`handshakeSteps.ts`, `Sandbox.tsx`) — the doc's fix explicitly said one prominent placement resolves the issue without requiring a rewrite of the terms themselves.
This is the single highest-value finding in this review, because it affects the site's core credibility claim (teaching "network and security fundamentals," not one vendor's product). "App-ID," "User-ID," and "Content-ID" appear as unqualified concepts in `handshakeSteps.ts` (all three `SCENARIOS`), `glossary.ts` (`firewall` category, lines 13–15), `Sandbox.tsx` (the entire "Match on" mechanic is literally built around these three names), and nowhere in any of that copy is it noted that these are one specific vendor's branded names for ideas that every NGFW vendor implements under different names (application awareness/deep packet inspection, identity-based policy, content/threat inspection are the generic equivalents; Fortinet, Check Point, Cisco, and others all have their own product-specific names for the same underlying ideas). A learner who works through this entire site and then opens a real firewall from a different vendor will not find "App-ID" or "User-ID" anywhere in that product's UI or documentation, and nothing in Netwise prepared them for that. For a site whose stated premise is teaching fundamentals to complete beginners, presenting vendor-branded terminology as if it were the industry-standard vocabulary is the kind of thing that actively misleads rather than just simplifies.
*Fix:* Add one clarifying note, ideally placed where a reader first encounters this vocabulary in a narrative chapter (Chapter 3's stepper, or the static App-ID/User-ID/Content-ID recap recommended in Finding C3-5) and reinforced in the Glossary. Something like: *"App-ID, User-ID, and Content-ID are one major firewall vendor's names for these capabilities — every modern firewall does some version of 'identify the real application,' 'know who's sending it,' and 'inspect the content for threats,' but the product-specific names differ vendor to vendor. This site uses one vendor's naming throughout for consistency, since the underlying ideas transfer regardless of which product you eventually work with."* This single addition (one paragraph, placed once prominently, referenced or footnoted elsewhere) resolves the issue without requiring a rewrite of the vendor-specific terms themselves — the terms are fine to teach with (they're concrete and well-documented), they just need honest framing.

The "MAC" acronym is defined only as "Message Authentication Code" (`acronyms.ts` line 18), which is correct for its only current use (`cipherSuite.ts`'s SHA384 entry), but "MAC" much more commonly means "Media Access Control address" in general networking. If a future chapter ever touches switching/Layer 2 topics, this tooltip will be actively wrong in that context.**
❌ **Skipped (per doc: "No action needed today").** Revisit if/when L2/switching content is ever added.
